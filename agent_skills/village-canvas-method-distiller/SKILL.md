# Village Infinite Canvas 方法蒸馏

把一个已经做成的创作流程变成可重复能力，不是把聊天记录改写成教程。必须先证明原流程
真实发生过，再提取跨项目仍然成立的判断点，最后用独立请求测试新 Skill。

本 Skill 与 `village-canvas-engineering-governance` 的分工：

- 工程治理管代码改动、合同、回归和运行态；
- 方法蒸馏管创作流程、画布/ Run 血缘和 Skill 形成。

## 一、何时加载

- 用户问“这个片子/节点/画布是怎么做出来的”；
- 需要把一次成功创作沉淀成可复用 Skill；
- 同一类创作方法已经重复出现；
- 需要分析参考画布、Run 或工作流并提取方法；
- 已有 Skill 太模糊、太长或会触发错误任务，需要重写；
- 需要判断一个方法应该成为 Skill、脚本、现有 Skill 更新，还是一条项目规则。

一次探索、纯闲聊、含密钥的临时操作和只对单张素材有效的做法，不沉淀为 Skill。

## 二、只读取证

分析原流程时默认只读：

```text
画布快照：节点、连线、参数、revision
节点血缘：输入、输出、引用和替换关系
任务事实：任务终态、provider、产物回读
Run 事实：阶段、checkpoint、verifier、发布门
人工步骤：选择、审核、返工和最终保留原因
```

不得读取或写入密钥、Cookie、私人正文和未授权媒体。画布写入、生成任务、安装技能等
有副作用动作必须与“分析”分开授权。

## 三、重建因果链

按以下格式重建真实流程：

```text
目标
  -> 初始输入
  -> 关键判断
  -> 工具/模型动作
  -> 中间产物
  -> 质量检查
  -> 失败与返工
  -> 最终产物
```

每个步骤区分：

| 类型 | 规则 |
|---|---|
| 画布事实 | 节点、连线、revision 和回执可直接证明 |
| 任务事实 | 任务终态、provider 和产物可回读 |
| 用户决定 | 审核、选择和主观取舍 |
| 合理推断 | 从事实推断，但未被直接记录 |
| 未知 | 凭据、未保留日志或缺失证据 |

不能把“看起来像用了某模型”写成事实。推断必须标注依据和不确定点。

## 四、找承重步骤

不是所有步骤都值得写进 Skill。承重步骤满足至少一项：

```text
改变最终质量
避免高成本失败
决定身份、叙事、风格或声音一致性
提供关键恢复点
把模糊要求转成可执行判断
在其它题材中仍可复用
```

只记录动作而不解释判断，等于把读者留在原地。必须写清：

```text
什么时候做
看什么信号
为什么做这个选择
什么情况下不做
失败时退到哪里
```

## 五、去模板化

从原流程中删除：

- 一次性角色名、台词、具体创意和私人项目值；
- 某个供应商独有参数，除非当前注册表已证实可用；
- 为单次任务写死的时长、尺寸、模型和价格；
- 可以由现有工具动态发现的事实；
- 泛泛而谈的“保持高质量、注意一致性”。

保留：

- 触发条件与不触发条件；
- 必需输入和缺失输入处理；
- 决策顺序、优先级和冲突处理；
- 工具能力边界；
- 失败恢复；
- 输出合同与验收标准；
- 最小真实评测用例。

## 六、Skill 边界

新 Skill 必须回答：

```text
它只解决什么问题？
它明确不解决什么问题？
与最近似的现有 Skill 如何分工？
实现前需要哪些真实输入？
哪些动作会产生费用或持久副作用？
成功与失败分别如何判定？
```

名称使用项目原生 `village-canvas-*` 命名空间。目录名与 frontmatter `name` 必须一致。
`description` 在第一屏内说清用途、适用场景和边界，不堆触发词。

## 七、写最小评测

每个新 Skill 至少设计三类请求：

| 类型 | 目的 | 通过条件 |
|---|---|---|
| 典型请求 | 应被正确触发并产出合同 | 使用正确工具，结果结构与边界正确 |
| 近似但不适用 | 应触发相邻 Skill 或明确不触发 | 不抢别的 Skill 责任 |
| 缺输入/冲突 | 应暴露缺口而不编造 | 明确待确认、停止在副作用前 |

评测必须使用真实 Skill 加载和真实任务上下文。可以隔离运行，但不能用假模型结论证明
“Skill 有效”。

若有条件，再做一次前后对照：

```text
无 Skill 时：常见错误是什么？
有 Skill 时：同一错误是否消失？
是否引入新的过度触发、冗余步骤或副作用？
```

## 八、落盘与验证

只创建实际需要的文件。通常只有：

```text
agent_skills/<village-canvas-name>/SKILL.md
```

只有存在可复用脚本、schema 或模板时才增加 `scripts/` 或 `references/`。

落盘后：

1. 用 `skill(action="list")` 确认真实可见；
2. 用 `skill(action="load", name="...")` 确认完整正文可读；
3. 运行相关合同测试和产品身份检查；
4. 检查新 Skill 与现有 Skill 的描述和职责重复；
5. 更新 `agent_skills/INDEX.md`；
6. 若运行版使用独立目录，再按部署链同步并回读，不只改开发态文件。

## 九、质量反模式

直接拒绝以下产物：

- 把旧平台菜单、UI 步骤或供应商名抄成“方法”；
- 只列概念，没有触发、输入、判断、恢复和输出；
- 复制完整旧模板，造成运行时上下文膨胀；
- 同一个 Skill 同时负责选角、分镜、生成、混音和交付；
- 把缺少证据的经验写成稳定规则；
- 为一次失败永久设置过度保守的全局限制；
- 新 Skill 与现有 Skill 88% 以上职责重叠；
- 文档声称已安装或已验证，但运行时目录和加载回执不支持。

## 十、输出合同

```text
source_scope
evidence_refs
load_bearing_steps
fact_inference_boundary
reusable_method
candidate_skill_boundary
evaluation_cases
draft_skill
installation_evidence
remaining_unknowns
```

## 十一、验收清单

- [ ] 原流程事实、推断和未知项已分开。
- [ ] 只提取承重判断，没有复制一次性项目内容。
- [ ] 新 Skill 有明确触发与不触发边界。
- [ ] 与现有 Skill 有可解释的分工，没有重复能力。
- [ ] 三类评测用例覆盖成功、误触发和缺输入。
- [ ] 真实目录、真实加载和安全测试通过后才说“已安装”。
- [ ] 索引已更新；有运行版时完成部署与回读。
- [ ] 未经验证的创作效果没有被写成稳定能力。

## 来源与边界

本 Skill 蒸馏自历史技能归档中的 `explain-how-it-made` 与 `skill-creator`，
并结合村长原生 `skill` 工具、`agent_skills/` 和 `skills_distill` 的真实边界。
它不复制外部平台的技能目录、安装器、偏好记忆或运行时控制面。
